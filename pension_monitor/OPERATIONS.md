# 운영 가이드

## 실행 방식
- **정기**: 평일(월~금) 06:07 KST 예약(`pension-events` 워크플로, cron `7 21 * * 0-4` UTC).
  GitHub 예약 실행은 지연될 수 있다(2026-11 실측 중앙값 4시간 — 그래서 혼잡 시간대를 피해 옮겼다).
- **수동**: `workflow_dispatch`. 코드 검증은 `collect-test` 워크플로(DB 쓰기·메일 없음)를 쓴다.
- 정기 실행은 **기본 브랜치(main) 코드**로 돈다. 머지되지 않은 수정은 효과가 없다.
- 날짜(리포트 파일명, 종료 판정, 종료 임박)는 모두 **한국 날짜** 기준이다(`config.today_kst`).
- `TRIGGER_TYPE` 값 `weekly` 는 "예약 실행"이라는 뜻이다(평일 매일). DB 제약이 `weekly|manual`
  만 허용해 이름을 그대로 둔다.

## 비용
- 파이프라인은 순수 Python 이며, 외부 LLM 은 **Gemini(무료 티어)** 만 쓴다 — 상세 본문·배너
  이미지의 구조화 추출용. 호출은 캐시가 줄인다: 원문 해시가 같으면 부르지 않는다.
- 사람/Claude 가 결과를 들여다볼 때의 토큰은 별도다. 아래 순서로 보면 최소로 끝난다.

## 실행 결과 확인 순서 (작은 것부터)
1. **메일 제목** — 수집 실패가 있으면 `⚠수집실패 증권사(N회 연속·사유)` 로 시작한다.
2. **`data/last_run_summary.json`** (1KB 미만) — 아래 표의 필드.
3. **Step Summary 한 줄** — 같은 수치 + 단계별 소요 시간.
4. `reports/latest.md` — 리포트 전문.
5. 그래도 원인이 안 보일 때만 잡 로그(`tail_lines` 를 작게). 로그는 줄마다 실제 시각이 찍힌다.

| 필드 | 뜻 | 정상 범위 / 볼 것 |
|---|---|---|
| `firms_failed`, `fail_reasons`, `fail_streak` | 수집 실패 증권사 · 사유 · 연속 횟수 | 비어 있어야 정상 |
| `llm_calls`, `llm_reasons` | Gemini 호출 수 · 캐시 미스 사유별 | `hash_changed` 가 매일 같은 증권사에서 나오면 원문 해시가 불안정한 것 |
| `cache_hits` | 캐시 적중 이벤트 수 | 진행중 건수에 가까울수록 좋다 |
| `review_count` | 검토 필요 건수 | 상시 3건을 넘으면 사유 분포 확인 |
| `hash_changed`, `hash_changed_parts` | 직전 실행 대비 원문 해시가 바뀐 이벤트 수 (본문/이미지 성분별) | 상세는 `data/hash_inputs.json` 의 `changed_from_prev` |
| `timings` | 목록/상세/정규화/DB 소요(초) | 합계 10분 이내 |

## 수집 실패 대응
- 사유: `redirected`(목록이 다른 사이트로 이동) · `empty_shell`(틀만 뜨고 목록 없음) ·
  `selector_zero`(본문은 있는데 목록 구조가 다름 — 마크업 변경 의심) · `timeout` · `error` ·
  `zero_items`(0건, 원인 미분류).
- 같은 증권사가 **2회 연속** 실패하면 잡이 실패(빨강)로 끝난다. 리포트·메일·산출물 커밋은
  그대로 수행된 뒤다. 임계값은 환경변수 `FAIL_STREAK_ALERT`.
- 실패한 증권사의 기존 진행중 건은 리포트에 유지되며 최종 확인일이 함께 표기된다.

## 검토 필요 표기 읽는 법
- **재추출 대상** (다음 실행에서 다시 추출, 같은 원문 기준 주당 최대 3회): 근거 불일치, 목록
  요약 폴백, 혜택 미확인, 유실 차단("부분집합(유실만)").
- **정보성** (원문이 바뀔 때까지 캐시 유지, 사람이 확인): 기간 불일치(목록 vs 상세), 요일
  불일치, 종료일 추론, 기간 미확인, 기간 충돌, 대상계좌 미확인, 조항 추출 누락(G8).
- 분류표는 `normalize.INFORMATIONAL_MARKERS`. 새 사유를 추가하면서 분류를 빠뜨리면 재추출
  대상으로 취급된다(보수적 기본값).

## 검증용 워크플로 (`collect-test`)
- `llm=false` : Gemini 를 부르지 않고 수집·해시 계측만. 두 번 돌리면 그 사이 해시를 바꾼
  성분이 `data/hash_inputs.json` 에 남는다.
- `use_db=true` : 기존 DB 행을 읽기만 해서 캐시 판정을 운영과 같은 조건으로 재현한다.
  "이 브랜치 코드면 Gemini 가 몇 콜 나가는가"를 머지 전에 잴 수 있다.
- 실행한 브랜치에 `data/` 를 커밋한다. 검증이 끝나면 main 의 `data/` 로 되돌린 뒤 머지한다.

## 테스트
- `python tests/test_offline.py` — 외부 호출 없는 로직 검증 (PR/푸시마다 CI 실행).
- `python tests/test_scraper_browser.py` — 로컬 가짜 사이트를 실제 Chromium 으로 여는 스크레이퍼
  검증 (playwright 필요, CI 의 `scraper-browser` 잡).

## 디버깅
- 이벤트 전건/리포트 전문을 stdout 에 보려면 `DEBUG=1`.
- 관측 비용을 키우는 것: 워크플로 실행 목록 전체 조회(응답 100KB+), 잡 로그 전문 조회.
  완료 여부는 `git fetch` 후 브랜치 HEAD 변화로, 내용은 위 1~4 순서로 본다.
